1. ISSUE SUMMARY
================================================================================

TEST: `WorkflowEngineContractTest.terminalStatePersistedBeforeEvent`

ORIGINAL ISSUE: Test was intermittently failing with AssertionError in the full test suite, but passing in isolation.

ROOT CAUSE: Race condition in test synchronization logic.

The test had a flawed synchronization mechanism:
1. `engine.createWorkflow("persist-terminal", nodes)` - Creates and persists workflow (QUEUED state)
2. `engine.execute(workflow.id)` - Starts execution, launches monitorWorkflow coroutine
3. `waitForTerminal(workflow.id, engine)` - Waits for workflow to reach terminal state (FAILED)
4. `waitForPersist(storage)` - Waits for storage to have data

BUG: `waitForPersist` checked if storage had ANY data, but the workflow was ALREADY persisted during `createWorkflow` (in QUEUED state). So `waitForPersist` returned immediately without waiting for the terminal state (FAILED) to be persisted.

Then the test checked:
- `persisted.contains("FAILED")` - but the terminal state (FAILED) might not have been persisted yet by the monitorWorkflow coroutine
- `capturedEvents.any { e -> e.source.contains("workflow_") }` - the event might not have been published yet

================================================================================
2. ROOT CAUSE ANALYSIS
================================================================================

The test's synchronization logic was flawed:

```kotlin
// Original waitForPersist - CHECKS ANY DATA, NOT TERMINAL STATE
suspend fun waitForPersist(storage: TestStorage) {
    val start = System.currentTimeMillis()
    while (System.currentTimeMillis() - start < 5000) {
        val encoded = storage.getString("aethra.workflows.v1")
        if (encoded != null && encoded.isNotEmpty()) return  // BUG: returns immediately because workflow was persisted during createWorkflow
        delay(10)
    }
}
```

The workflow was persisted TWICE:
1. During `createWorkflow()` - in QUEUED state
2. During `monitorWorkflow()` - in FAILED/COMPLETED state

`waitForPersist` returned after step 1, not waiting for step 2.

3. FIX APPLIED
================================================================================

FILE MODIFIED: `core/src/test/kotlin/org/aethra/core/workflow/WorkflowEngineContractTest.kt`

CHANGES:
1. Replaced `waitForPersist(storage)` with `waitForWorkflowPersistedInTerminalState(storage, workflow.id)`
2. Added `waitForWorkflowEvent(capturedEvents, workflow.id)` to wait for event publication
3. New helper functions:
   - `waitForWorkflowPersistedInTerminalState()` - waits for specific workflow to reach terminal state (FAILED/COMPLETED/CANCELLED) in storage
   - `waitForWorkflowEvent()` - waits for workflow event to be published for specific workflow

NEW HELPER FUNCTIONS:
```kotlin
private suspend fun waitForWorkflowPersistedInTerminalState(storage: TestStorage, workflowId: String) {
    val start = System.currentTimeMillis()
    while (System.currentTimeMillis() - start < 5000) {
        val encoded = storage.getString("aethra.workflows.v1")
        if (encoded != null && encoded.isNotEmpty()) {
            if (encoded.contains(workflowId) && (encoded.contains("FAILED") || encoded.contains("COMPLETED") || encoded.contains("CANCELLED"))) {
                return
            }
        }
        delay(10)
    }
    fail("Workflow $workflowId did not reach a terminal state in storage within 5 seconds")
}

private suspend fun waitForWorkflowEvent(capturedEvents: MutableList<TaskEvent>, workflowId: String) {
    val start = System.currentTimeMillis()
    while (System.currentTimeMillis() - start < 5000) {
        if (capturedEvents.any { e -> e.source.contains("workflow_") && e.taskId == workflowId }) {
            return
        }
        delay(10)
    }
    fail("Workflow event for $workflowId was not published within 5 seconds")
}
```

6. CONCLUSION
================================================================================

The intermittent failure of `terminalStatePersistedBeforeEvent` was caused by a race condition in the test's synchronization logic, not a bug in the production code.

The test's `waitForPersist` helper incorrectly returned early because it checked for ANY data in storage, but the workflow was already persisted during creation (in QUEUED state). The fix ensures the test waits for:
1. The specific workflow to reach a terminal state (FAILED/COMPLETED/CANCELLED) in persistent storage
2. The corresponding workflow event to be published

All tests now pass consistently. The fix is minimal, targeted, and preserves all existing test coverage while eliminating the race condition.
